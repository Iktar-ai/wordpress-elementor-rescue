# Concrete delivery examples

These are hypothetical acceptance examples, not completed client work or evidence that a particular client site passed. Replace example identities, counts and results with observed project evidence.

## Example 1: repair a business website

**Request:** “Our Elementor site is on Hostinger. Two service icons are empty, hover is missing and the contact section looks wrong. Keep our design and let us edit it.”

**Expected delivery:** The existing WordPress site remains editable. A protected preview demonstrates the agreed icon, interaction, typography and spacing repairs. A focused PR contains the durable source changes, relevant before/after evidence and rollback instructions. The form stays clearly in preview mode until its real delivery path is separately authorised and tested.

**Acceptance:** Native Elementor edit/save is verified; the repaired icons load; hover/focus/touch behavior works; reduced-motion preferences are respected; agreed mobile/desktop routes have no new overflow. Runtime and exact-version independent review pass. Private access remains intact.

**Example final report, only when those facts are evidenced:**
> The two missing icons and service-card interactions are repaired in the protected preview. The contact layout is corrected; sending remains disabled for the preview. Elementor editing and the agreed browser checks passed. The reviewed PR and rollback are ready. Production release awaits the outstanding owner decision.

If browser access is blocked, replace the pass with BLOCKED and say exactly which native checks remain. Never copy this sample verdict as evidence.

## Example 2: recover a complete site into a new Hostinger environment

**Request:** “The previous developer has handed over WordPress, Elementor exports, media and a database backup. Move the site, preserve its URLs and editing, and fix anything that breaks.”

**Expected delivery:** A recovered native WordPress installation with working pages, media, navigation, theme/templates, forms within the approved integration scope, and client editing. An inventory distinguishes complete backups from partial Elementor exports. Supported plugin/licence dependencies and missing items are explicit. A protected preview is demonstrated before the authorised cutover.

**Acceptance:** Files/database coverage is verified, sensitive data stays in its approved boundary, outbound effects are isolated during preview, templates/dynamic features survive, URLs and redirects are checked, and a coherent restore is demonstrated. DNS and email records are preserved. Release verification includes real form delivery only where authorised.

**Example result after an authorised successful cutover:**
> The recovered site is live on the approved Hostinger destination and remains editable in WordPress/Elementor. The agreed routes, redirects and authorised form delivery passed. The previous environment remains available for the agreed rollback period. Handover includes the source PR, dependency/licence register, backup/restore instructions and the outstanding maintenance items.

Do not promise zero downtime, identical plugin behavior, preserved SEO rankings or a successful migration before these checks.

## Example 3: a live store needs a narrower release

**Request:** “Publish our fixed staging site now; we have received 27 new orders since it was copied.”

**Expected delivery:** An explicit release decision based on what changed. If only CSS/plugin code changed, prepare and test a bounded file/configuration release that preserves the live database. If data/schema changes are necessary, prepare an approved freeze/delta and payment-event reconciliation plan. Do not use a full staging publish merely because it is one button.

**Example checkpoint:**
> The visual repair is ready. Full staging publication would replace newer live data, so it is not an accepted release path. The proposed code-only release preserves the live database; its exact files, rollback and checks are recorded. Any remaining release authority or test gap is stated explicitly.

The diagnostic can be complete while migration or production release remains pending.

## Example 4: only screenshots and a public URL exist

**Request:** “Copy this old Elementor site into Codex. We have no administrator access, backup or plugin licences, but need to keep editing it.”

**Expected delivery:** A bounded feasibility/access assessment, a list of missing source/rights, and the viable recovery or separately scoped replacement options. Screenshots can guide a new implementation; they cannot establish original editable source recovery. Do not sell a complete native migration on this evidence or silently substitute a static/React copy.

## Client handover contract

| Deliverable | What the client should actually receive |
|---|---|
| Working result | The agreed native website repairs or recovery, demonstrable at the authorised destination |
| Editing ownership | Verified WordPress/Elementor access and an edit/save walkthrough; licences and renewal responsibility identified |
| Source record | Focused versioned changes and nonsecret dependency/asset inventory in the client repository |
| Acceptance evidence | Per-item PASS/FAIL/NOT RUN/BLOCKED, exact reviewed/applied version and meaningful browser/runtime results |
| Recovery | Backup identity, restore route, tested rollback scope and known limitations |
| Operating boundary | Clear production/preview distinction, active vs disabled integrations, maintenance owner and remaining decisions |

Commercially, start with a paid diagnostic capped by time and scope. Quote the rescue after source, access, dependencies and continuity are known. Track actual diagnostic/build/rework hours on pilot engagements before claiming a standard margin or fixed turnaround. Describe case-study outcomes only to the extent supported by recorded evidence.
